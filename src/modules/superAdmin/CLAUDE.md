# superAdmin module

Super Admin's console: dashboard, users, relationships, and the teacher-connection process. **Role:** SUPER_ADMIN only (`routes/admin.routes.js` guards everything with `requireRole(SUPER_ADMIN)`). Master data is its own module (`masterManagement`), and subscriptions/payments are in `subscription`.

## API (all under `/admin`)
Users: `GET|POST /users`, `GET|PATCH|DELETE /users/:id`, `POST /users/:id/suspend|reactivate|reset-password`, `GET|POST /users/:parentId/children`, `GET /roles`, `GET /subjects`
Family (any parent of the family; `parent.service#admin*` resolves the account holder): `GET /users/:id/family`, `POST /users/:id/family/parents`, `POST /users/:id/family/parents/:memberId/activate|deactivate`, `POST /users/:id/children/:childId/activate|deactivate`; deleting a child or extra parent is `DELETE /users/:id`
Relationships: `GET /relationships`, `/relationships/grouped`, `POST /relationships`, `PATCH|DELETE /relationships/:id`
Connections: `GET /teacher-connections`, `GET /teacher-connections/changes`, `POST /teacher-connections`, `PATCH /teacher-connections`, `POST /teacher-connections/move`, `POST /teacher-connections/remove`
Invitations: `GET|POST /teacher-invitations`, `POST /teacher-invitations/:id/approve|reject|accept-for-teacher|resend|cancel`
Email copy: `GET /email-copy`, `GET|PUT|DELETE /email-copy/:name`, `POST /email-copy/:name/preview`

## Rules - read before changing
- **One teacher per subject, per student, per academic year (2026-10-19, user request):** `services/teacherSubjectCoverage.service.js` - a subject is taken when a teacher is actively connected for it, or a request (`awaiting_approval`) or a sent, unexpired invitation for it is open; links/invitations without a year count as the current year's. Enforced on the parent's request, Super Admin's send (per pair, including earlier pairs of the same send), approve (409 "Reject this request instead"), the teacher's Accept (409, never names the other teacher) and resuming a paused link (`relationship.service#updateRelationshipStatus`). The assisted-connection APIs (UI removed) check it too (2026-10-20): `teacherConnection.service` create / edit (added subjects or a new year) / move (after the old rows are gone, in the same transaction) - the teacher's own rows don't count. Tests `tests/integration/teacherSubjectRule.itest.js`, `scenarios/teacher-assignment-flow.mjs`, `functional/teacher-assignment-http.mjs`.
- **Super Admin's invitations reach the family (2026-10-19):** every one sent notifies the child's parents in-app ("Growing Focus invited … for 2026-2027 … follow it on My Children", type `teacher_invitation_approved`); the parent sees it on the child card with its progress.
- **The connection process:** parent sends a request (`awaiting_approval`) → Super Admin approves (fresh token, status `pending`, client-written email to the teacher) or rejects (`rejected` + `review_note`, which the family sees) → the teacher accepts/declines. Only `awaiting_approval` can be approved or rejected. A rejection note must be at least 5 characters.
- **Assisted changes are exceptions,** not the normal path. Every create/edit/move/remove/accept-for-teacher requires a **reason** (min 5 characters), writes an `audit_logs` row (actor, before/after, reason), and appears in the Change log. The reason is internal and **never shown to the family**.
- **Families are always told:** every assisted change notifies the child's parents in-app (`NOTIFICATION_TYPES.TEACHER_CONNECTION_UPDATED`), in plain words, without the reason.
- **Moves merge:** moving subjects to a teacher who already teaches the student must add to their connection, never wipe it (`writeSubjects({ merge: true })`). The same applies to a year change.
- Editing a connection can switch the teacher. That is a hand-over (`moveConnection`), not an in-place update.
- The one-open-invitation rule is a DB partial unique index (`uq_teacher_invitations_one_pending WHERE status IN ('pending','awaiting_approval')`). `blockerFor({ excludeId })` checks it in the service.
- **Invitation email copy:** `services/email/copy/teacher-invitation.txt` still has `[CLIENT COPY PENDING]` slots. In production, send/approve/resend is blocked until they're filled (`assertCopyReady`): **409 `INVITATION_EMAIL_NOT_READY`** "Teacher invitations can’t be sent yet: the invitation email is still waiting for its final wording. Nothing was sent…" (was a 503, which the app words as "being updated, try again in a few minutes" - QA 2026-10-21 reported it as "error when inviting a teacher" / "error creating an assignment"). Invite Teachers shows it in the dialog, Approve & send as a toast. A saved `email_copy` row overrides the file. With the editor page hidden, fill the file.
- Direct linking without an invitation was removed on purpose (`bulk-assign` is gone). Don't bring it back without asking.
- Row actions are icon buttons with semantic colours (delete red, activate green, deactivate amber, edit/view accent). Filters use a compact `FilterBar`.
- **Families (2026-10-09, user request):** Super Admin creates the parent; nothing can be added to the family - by the admin or the parent - until the parent subscribes (`family.service` "no subscription plan in force", also for `POST /relationships` parent_child). Then children and extra parents up to the plan, counting **active** members only; deactivating is always allowed, activating needs a free place. **A parent who still has children or other parents can't be deleted** (`user.service#deleteUser` 409 with `children`/`parents` details - before, deleting one orphaned their children); an extra parent can be. A parent with billing history still can't be deleted (409 "has billing history... Suspend instead"). The old Unlink (one parent's link only) is gone from the panel.

- **Parents list = account holders (2026-10-21, user request):** `/admin/users/parents` sends `accountHoldersOnly=true` (`GET /admin/users`, `user.repository#listUsers` `excludeExtraParents`: no `co_parent` link pointing at the user). Extra parents are reached from their account holder's record (Family panel). Other callers and the dashboard's counts are unchanged. Tests `scenarios/admin-list-paging.mjs`, `functional/family-parent-edit-http.mjs`.
- **Back on a user's record (2026-10-22, user request):** `UserDetailPage` has a Back button above the header (`userBack.js#userBackTarget` + test). A link that opens a record passes `state={backTo(path, label)}`: the family panel → "Back to <parent>", Assignments → "Back to Assignments"; Edit hands that state back on Save and Cancel. Opened any other way → "Back to Students/Parents/Teachers", the list as it was left (`listAddress`). Test `.claude/testing/scenarios/admin-user-back.mjs` (11).
- **Lists keep their place (2026-10-20, user request):** Students / Parents / Teachers (`UsersListPage`), Assignments (`RelationshipsPage`: search, teacher, student, subject, grade, year, status) and Teacher invitations (search, status; "Show requests" sets `status=awaiting_approval`) keep filters, sort, page and rows per page in the address (`hooks/useListQuery`, search boxes `hooks/useAddressText`) and always show the pager with Rows per page. The server pages them (`validators/common.js#paginationQuery`, limit up to 100). Back from a user's record, a reload or a shared link shows the list as it was. Test `scenarios/admin-list-paging.mjs`.
